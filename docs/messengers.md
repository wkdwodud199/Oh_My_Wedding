# 메신저 연동 조사

확인일: 2026-11-01, Asia/Seoul. 공식 개발 문서와 카카오 공식 개발자 지원 포럼을 확인했다. 아래 추천은 기능 적합성에 대한 구현 판단이며, 외부 서비스 계정이나 봇을 생성하거나 메시지를 발송한 상태는 아니다.

## 결론

첫 실행은 **두 사람 + Telegram 봇이 들어가는 그룹**이 가장 단순하다. 정기 공지와 시트 변경 명령을 같은 방에서 처리할 수 있고, `getUpdates` long polling을 쓰면 공개 웹훅 서버도 필요 없다. 카카오톡은 기존 커플 단톡방에 외부 봇을 넣어 자동 송수신하는 공식 API가 없어 요구한 경험을 그대로 만들기 어렵다. Discord를 이미 사용한다면 전용 서버의 텍스트 채널도 좋은 대안이다.

| 방식 | 정기 공지 | 대화에서 수정 명령 수신 | 두 사람이 함께 보는 공간 | 이 프로젝트의 판단 |
| --- | --- | --- | --- | --- |
| 카카오톡 기존 일반 단톡방 | 공식 서버 API로 불가 | 일반 채팅 수신 API 없음 | 기존 단톡방 | 양방향 자동화 대상으로 선택하기 어려움 |
| 카카오톡 공유 SDK | 사용자의 공유 동작 필요 | 불가 | 사용자가 고른 단톡방 | 수동 공유 버튼 용도 |
| 카카오톡 나에게 보내기 | 사용자 토큰으로 가능 | 일반 채팅 답장 수신 불가 | 각자의 나와의 채팅 | 별도 개인 알림용 보조 수단 |
| 카카오톡 채널·챗봇·알림톡 | 해당 상품·권한·심사 조건에 따라 가능 | 채널 챗봇 스킬로 가능 | 고객과 채널 간 대화 | 개인 커플 프로젝트에는 설정 부담이 큼 |
| Telegram 그룹 봇 | 가능 | 명령·봇 메시지 답장 수신 가능 | 공유 그룹 | 첫 구현 권장 |
| Discord 서버 채널 + 봇 | 가능 | 슬래시 명령으로 가능 | 공유 텍스트 채널 | 차선 권장 |
| Discord incoming webhook만 사용 | 가능 | 시트 변경 명령 처리는 별도 앱 필요 | 공유 텍스트 채널 | 공지만 먼저 붙일 때 적합 |

## 카카오톡: 가능한 기능의 경계

카카오 공식 지원 답변은 일반 카카오톡 채팅의 송수신 API를 제공하지 않으며, 시스템 메시지 수발신은 채널의 챗봇·상담톡을 이용하도록 안내한다. 이 답변은 2024-09-05 게시됐으며, 확인일 현재 메시지 REST API의 대상도 나 자신 또는 조건을 만족하는 친구로 정의된다. 따라서 기존 커플 단톡방을 방 ID로 지정하여 정기 발송하거나 방 대화를 읽는 기능은 공식 공개 API 범위에 없다. [공식 지원 답변](https://devtalk.kakao.com/t/api/139501), [메시지 REST API](https://developers.kakao.com/docs/ko/kakaotalk-message/rest-api)

카카오톡 공유는 사용자가 버튼을 누르고 친구 또는 채팅방을 선택하는 흐름이다. 단톡방으로 공유할 수 있다는 사실이 무인 정기 발송을 의미하지 않는다. [공유 흐름](https://developers.kakao.com/docs/ko/kakaotalk-share/common)

친구에게 보내기는 친구 목록 정보 제공 조건과 사용 권한이 적용되며, 나에게 보내기는 로그인한 사용자 본인에게만 발송한다. 확인일 문서에는 심사 전 친구 발송 테스트 일 30건과 심사 후 쿼터가 안내되어 있다. 이 테스트 범위를 일반 단톡방 API로 해석하면 안 된다. 실제 토큰 수명·갱신 및 운영 권한은 선택 시 다시 설정해야 한다. [권한·쿼터](https://developers.kakao.com/docs/ko/kakaotalk-message/common), [수신 대상](https://developers.kakao.com/docs/ko/kakaotalk-message/rest-api)

알림톡은 정보성 메시지이며 사전 승인된 템플릿을 사용한다. 시작하려면 채널 개설, 비즈니스 채널 전환, 공개·고객센터 설정 및 공식 딜러사 계약이 필요하다. 발송 단가는 딜러사별로 다르므로 여기서는 고정 가격을 추정하지 않는다. 임의의 업체 조사 요약이 심사 승인된다는 보장도 없다. [카카오 알림톡 가이드](https://kakaobusiness.gitbook.io/main/ad/infotalk.md)

채널 챗봇은 사용자 입력을 외부 기능에 연결할 수 있으나, 실제 예약 등 업무 처리는 스킬 개발이 필요하다. 이는 기존 일반 단톡방과 다른 이용 흐름이다. [챗봇 기획·스킬 안내](https://kakaobusiness.gitbook.io/main/tool/chatbot/tutorial/chatbot_planning)

비공식 카카오톡 클라이언트나 PC 화면 자동화는 공식 API와 분리해 판단해야 한다. 앱 화면·로그인·기기 상태에 의존하는 방식은 안정적인 상시 봇의 첫 구현으로 채택하지 않는다. 이는 유지보수에 대한 판단이지, 모든 비공식 프로젝트의 현재 작동 여부나 제재 여부를 확인했다는 뜻은 아니다.

## Telegram: 최소 설정과 구현 방향

1. `@BotFather`에서 봇을 만들고 토큰을 발급한다.
2. 두 사람의 그룹에 봇을 추가한다. 그룹의 `chat_id`를 설정한다. 현재 구현은 지정된 방의 사람 메시지를 처리하며, 사용자 ID는 변경 기록의 요청자 구분에 사용한다. 두 사용자 ID를 별도로 설정하는 기능은 없다.
3. 기본 privacy mode를 유지하고 명시적인 명령 또는 봇 메시지에 대한 답장으로 요청한다. 일반 수다 전체를 읽어야 할 필요는 없다.
4. 작업 프로세스가 `getUpdates`로 명령을 받고 `sendMessage`로 결과를 보낸다. 외부에서 접속하는 공개 웹훅 URL은 이 방식에 필요하지 않다.
5. 프로세스를 항상 실행할 PC·NAS·서버를 정한다. PC가 꺼지면 정기 작업과 응답도 멈춘다.

봇은 사용자가 먼저 메시지를 보내거나 그룹에 추가해야 한다. 기본 privacy mode에서는 봇을 대상으로 한 명령과 관련 답장을 받는다. [봇 시작 안내](https://core.telegram.org/bots), [그룹·privacy mode](https://core.telegram.org/bots/features)

구현 시 `getUpdates`와 webhook은 동시에 사용할 수 없다. 처리한 `update_id + 1`을 저장하여 재시작 때 중복 변경을 줄인다. Telegram은 미수신 업데이트를 24시간 넘게 보관하지 않으므로 상시 실행이 중요하다. `sendMessage`는 4,096자 제한이 있어 긴 조사 보고서는 나누어 보내거나 시트 링크로 연결한다. [Bot API](https://core.telegram.org/bots/api)

권장 상호작용 예시(구체 명령명은 최종 구현 README 기준):

```text
목록: 현재 미정 항목과 다음 마감일 조회
수정: 작업 ID + 바꿀 필드 + 새 값 전달
결과: 변경 전 → 변경 후, 시트 반영 결과를 같은 방에 공유
조사: 지역·예산에 맞는 새 후보만 묶어서 공지
```

## Discord: 구현 가능한 대안

공지 전용이라면 채널 incoming webhook이 가장 간단하다. 다만 incoming webhook은 채널에 메시지를 게시하는 수단이므로 이것만으로 사용자의 수정 명령을 받는 기능이 완성되지는 않는다. [Webhook API](https://docs.discord.com/developers/resources/webhook)

양방향 기능은 Discord 애플리케이션·봇과 슬래시 명령을 사용한다. 두 사람만 사용하는 서버와 텍스트 채널을 만들고 봇에 해당 채널 보기·메시지 전송 권한을 부여하면 된다. 슬래시 명령의 입력은 interaction으로 전달되므로 일반 대화 전체를 읽는 구현을 피할 수 있다. [명령·상호작용](https://docs.discord.com/developers/interactions/overview)

Interaction 수신은 Gateway 또는 HTTP 방식 중 선택한다. HTTP로 받으면 공개 endpoint와 Discord 서명 검증이 필요하며, 처음 응답은 3초 내에 보내야 한다. 오래 걸리는 업체 조사는 먼저 지연 응답한 뒤 결과를 전송한다. Gateway는 WebSocket 연결을 유지하는 봇 프로세스가 필요하다. [Interaction 응답](https://github.com/discord/discord-api-docs/blob/main/developers/interactions/receiving-and-responding.mdx), [Gateway](https://docs.discord.com/developers/events/gateway)

## 공통 운영 원칙

- 시트는 일정·상태의 기준 데이터로 두고 메신저 어댑터만 교체 가능하게 한다.
- 조사 결과는 출처·확인일·가격 조건을 포함한다. 업체의 실제 예약 가능 여부는 확인 없이 확정하지 않는다.
- 같은 결과를 매번 재발송하지 않고, 새 후보·가격 변경·마감 단계 변화처럼 의미 있는 변화에 집중한다.
- 최초 연결 시 현재 시트를 자동 변환하지 않는다. 별도 데이터 표의 열 이름과 상태값을 합의하고 적용한다.
- 최소 토큰 관리·대상 방 확인·중복 처리 방지는 기능의 정확성을 위해 유지한다. 별도 회원가입·복잡한 권한 체계·과도한 보안 서비스는 추가하지 않는다.

이 문서는 메신저 기능 조사 결과다. 각 서비스의 운영 심사 승인, 실제 연결, 발송, 시트 쓰기 검증은 아직 수행하지 않았다.
